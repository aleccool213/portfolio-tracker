# AGENTS.md — working notes for agents

Guidance for AI agents (and humans) working in this repo. Read
[`PLAN.md`](PLAN.md) for the product vision and the small, single-PR milestone
roadmap. This file captures **how to work here without hitting the same
friction twice**.

## What this is

A self-hosted personal-finance dashboard for a Canadian household.
**Rails 8.1 + SQLite**, **Hotwire (Turbo/Stimulus) over import maps — no JS
build step**, warm hey.com-style UI. Deploys via Docker to a Raspberry Pi
(Kamal) and to Render for throwaway per-PR test deploys.

## Everyday commands

Use the project **binstubs** — they run through Bundler, so you don't need the
`rails` gem on `PATH`:

```bash
bin/rails server            # http://localhost:3000
bin/rails test              # unit + integration tests
bin/rails test:system       # system tests (see gotcha below)
bin/rails db:prepare        # create + migrate + seed
bin/rails db:seed           # (re)seed; seeds are idempotent

# The four checks this repo's CI runs — keep them all green:
bin/rubocop
bin/brakeman --no-pager
bin/bundler-audit
bin/importmap audit
```

Before opening/updating a PR, run **all of the above**. CI runs
`scan_ruby` (brakeman + bundler-audit), `scan_js` (importmap audit), `lint`
(rubocop), `test`, and `system-test`.

## Gotchas (learned the hard way)

### 1. `test/system/` must exist or `system-test` CI fails
The CI `system-test` job runs `bin/rails test:system`. If there are no system
tests **and no `test/system/` directory**, the runner raises
`cannot load such file -- test/system (LoadError)` and the job fails — even
though there's nothing to test. We keep `test/system/.keep` committed so the
task finds zero tests and exits cleanly. **Don't delete it.** When you add a
browser-driven feature, add a real system test here (Chrome is preinstalled on
GitHub runners and in this environment).

### 2. Never commit secrets or the database
`config/master.key` and everything under `storage/*.sqlite3` are gitignored —
keep it that way. (`rails new --skip-git` ships **no** `.gitignore`; ours was
added by hand. If you ever re-scaffold, recreate `.gitignore` before the first
`git add`, or you'll stage `master.key`, the SQLite files, `log/`, and `tmp/`.)
Quick sanity check before committing:

```bash
git status --short | grep -iE "master.key|\.sqlite3|/log/|/tmp/" && echo "STOP: don't commit these"
```

### 3. Deploy specifics
- **Render** (`render.yaml`): SQLite is **ephemeral and re-seeded on every
  deploy** — that's intentional for per-PR testing. The blueprint **bypasses
  Thruster** and binds Puma straight to Render's `$PORT`
  (`bash -lc "./bin/rails db:prepare && ./bin/rails server -b 0.0.0.0 -p $PORT"`),
  because Thruster defaults to port 80 which Render doesn't use.
  `SECRET_KEY_BASE` is generated by Render, so no `master.key` is needed there.
  If a milestone adds a model, **extend `db/seeds.rb`** so the preview has data
  (and satisfy any new validations on **create** — see §8).
- **Raspberry Pi** (persistent): the stock `Dockerfile` + Kamal
  (`config/deploy.yml`). SQLite persists on a volume under `storage/`.

### 4. Styling
Reuse the CSS custom properties and card patterns already under
`app/assets/stylesheets/` (split plain CSS files — `tokens`, `base`,
`components/*`; warm cream palette, rounded cards, light/dark aware). The
layout loads them via multiple `stylesheet_link_tag` entries (no CSS build
step, no `@import`). Add a new file + link tag when a feature needs its own
styles rather than growing one mega-file. **Never edit
`app/assets/stylesheets/application.css`** — that file was deleted in the
stylesheet split. Restacking an older branch that still patches it is a
modify/delete conflict: drop `application.css` and put the new rules in the
matching `components/*.css` (and add a `stylesheet_link_tag` if you added a
file).

### 5. This container's environment (only relevant for fresh tool installs)
- Ruby 3.3.6 and `bin/*` binstubs work out of the box. If you ever install the
  `rails` gem globally, its binary is at
  `/opt/rbenv/versions/3.3.6/bin/rails` (not on `PATH` by default) — prefer the
  binstubs regardless.
- The `sqlite3` **CLI** is not installed, but the `sqlite3` **gem** is — use
  Active Record / `bin/rails dbconsole`, not a bare `sqlite3` command.

### 6. Local macOS: rbenv shims must be first on `PATH`
Bare `bin/rails` in a login that still has `/usr/bin/ruby` first (system
Ruby 2.6) dies parsing `Gemfile` (`platforms: %i[ windows jruby ]`). Put
`~/.rbenv/shims` on `PATH` (or `eval "$(rbenv init -)"`) before any binstub.

### 7. Stack with Graphite, not plain git
This repo's stacked PRs are Graphite-managed (`gt`). After a restack, run
`gt submit --stack --no-edit --no-interactive` so Graphite and GitHub PR
bases stay in sync. A plain `git rebase` + `git push --force-with-lease`
leaves Graphite saying the remote "was not pushed with Graphite" / "need
submit", even when the SHAs match. After the **bottom** PR merges:

```bash
gt sync --no-interactive --delete-all
gt submit --stack --no-edit --no-interactive --update-only --branch <top-of-stack>
```

That retargets the next PR onto `master` (Render previews only fire for PRs
against the default branch — see §9).

### 8. Liability fields must be set on seed **create**, not a later `update!`
`Account` validations require `interest_rate` / `term_months` /
`original_principal` whenever `kind == "liability"`. On a fresh Render DB,
`find_or_create_by!(name:, institution:) { |a| a.kind = "liability" }`
saves immediately and **aborts `db:prepare`**. Put those fields in the
create attributes (the block only runs on create). A follow-up `update!` is
fine for re-seeds of already-created rows, but it never runs if create
failed. Reproduce with `bin/rails db:prepare` on an empty DB.

### 9. `scan_ruby` is Brakeman **and** bundler-audit
`bin/brakeman` always prepends `--ensure-latest`. An outdated gem (e.g.
8.0.5 vs 8.0.6) exits **5** with no findings — bump Brakeman, don't hunt
for warnings. The same CI job then runs `bin/bundler-audit`; that fails
separately on gem CVEs (`sqlite3`, `activestorage`/`rails`, `json`, …).
Before pushing:

```bash
bin/brakeman --no-pager
bin/bundler-audit
```

If audit reports a CVE, `bundle update <gem>` (or `rails` for Active
Storage) and commit `Gemfile.lock`.

### 10. Render PR previews
`render.yaml` has `previews.generation: automatic`. Render creates a
preview **only for PRs whose base is `master`**. A stacked PR targeting
`milestone-N` will not get one until it is restacked onto `master`. After
that, **push is enough** (`autoDeploy: yes`) — do not `trigger_deploy`
right after a push, you'll double-build.

If the PR was opened against a non-default base and later retargeted,
Render may not notice until a new commit lands. An empty
`Trigger Render PR preview.` commit (or any real follow-up commit) is
enough. The preview URL looks like
`https://portfolio-tracker-pr-<N>-….onrender.com`. Check with Render MCP
(`list_services` with `includePreviews: true`). First boot runs
`db:prepare` (migrate + seed); a seed validation error shows up as
`update_failed` in deploy logs, not a build failure.

### 11. System tests: this container's chromedriver is stale
`bin/rails test:system` fails here with
`session not created: Chrome instance exited` /
`This version of ChromeDriver only supports Chrome version 147`. Two container
quirks, neither of them a code problem (GitHub runners are fine):

- `/opt/node22/bin/chromedriver` (147) shadows the matched driver Selenium
  Manager would fetch. Drop it from `PATH` for the run.
- chromedriver then can't find a Chrome binary. Selenium Manager caches one
  under `~/.cache/selenium/chrome/linux64/<version>/chrome`; symlink it to
  `/usr/local/bin/google-chrome` (the `/opt/pw-browsers/chromium` Playwright
  uses is a different, older build — don't point at that one).

```bash
ln -sf /root/.cache/selenium/chrome/linux64/*/chrome /usr/local/bin/google-chrome
PATH=$(echo "$PATH" | tr ':' '\n' | grep -v '^/opt/node22/bin$' | paste -sd:) \
  bin/rails test:system
```

`test/application_system_test_case.rb` passes `--no-sandbox` /
`--disable-dev-shm-usage` so the suite runs as root in a container; both are
harmless on CI.

## Taking a screenshot (visual verification)

Handy since this app is mostly used from a phone. Start the server, then:

```bash
bin/rails server -p 3005 -b 127.0.0.1 &   # wait for /up to return 200
node script/screenshot.js http://127.0.0.1:3005/ tmp/shot.png 420 900
```

`script/screenshot.js` wraps the one non-obvious part: Playwright is a **global**
Node module here and must be `require`d by absolute path, using the preinstalled
Chromium. See the script header for details.

## Per-milestone checklist

1. Stay in the files the milestone lists; don't refactor unrelated code.
2. Add/extend tests as described; `bin/rails test` green.
3. Keep rubocop / brakeman / bundler-audit / importmap-audit clean
   (`bin/brakeman` must be the latest gem; see §9).
4. No JavaScript build step — Hotwire over import maps only.
5. If you add a model, extend `db/seeds.rb` (idempotent) so Render has data.
6. Match the existing warm hey.com styling.
